# ATHENA Authorisation Matrix
_Version 1.2 — 2026-10-02. Enforcement points: `athena-platform/server/src/middleware/auth.ts` (`authenticate`, `requireRole`, `requirePremium`, `requireSubscriptionTier`), `athena-platform/server/src/middleware/roles.ts` (role helpers), `athena-platform/server/src/middleware/resource-access.ts` (object-level policy), `athena-platform/server/src/config/public-routes.ts` (the routes that may be reached without signing in), Next.js middleware (coarse gate only)._

## Roles

| Role | Source | Description |
|---|---|---|
| anonymous | no token | Public pages, registration, login |
| MEMBER | `user.role` | Standard authenticated user |
| MENTOR | `user.role` | Member + mentor-side scheduling/earnings |
| EMPLOYER / COMPANY | `user.role` | Job posting, applicant management, org dashboards |
| CREATOR | `user.role` | Monetisation surfaces (uploads, payouts) |
| MODERATOR | `user.role` | Reports queue, content actions; no user PII beyond case need |
| ADMIN | `user.role` | Full admin surface; **must have MFA enabled [FOUNDER: enforce]** |
| service (internal) | `INTERNAL_SERVICE_TOKEN` header | Server-to-server; rate-limit bypass only, never user impersonation |

## Resource × action matrix (own = record owner only)

| Resource | anonymous | MEMBER | MENTOR | EMPLOYER | MODERATOR | ADMIN |
|---|---|---|---|---|---|---|
| Public pages, job search | read | read | read | read | read | read |
| Own profile / settings / sessions | — | CRUD own | CRUD own | CRUD own | CRUD own | CRUD any (audited) |
| Other users' profiles | public fields | public fields | public fields | applicants only | case-linked | any (audited) |
| Job applications | — | CRUD own | — | read for own jobs | — | any |
| Messages / chats | — | own threads | own threads | own threads | reported content only | reported content only |
| Mentor sessions / payouts | — | book | own calendar + earnings | — | — | any |
| Payments / subscriptions | — | own billing | own billing | org billing | — | refunds, config |
| Safety reports | submit (rate-limited) | submit + own | submit + own | submit + own | full queue | full queue |
| DV-safe housing data | — | own enquiries | — | own listings | — (no staff housing route) | need-to-know; every read of it is audited (see below) |
| Moderation actions | — | appeal own | appeal own | appeal own | act + log | act + log + policy |
| Admin panels (`/admin/*`, admin.routes.ts) | — | — | — | — | — | full |
| Feature flags, site settings | — | — | — | — | — | ADMIN only |

**DV-safe housing data, exactly.** "DV-safe" here is every confidential listing: DV-safe, emergency and transitional (`housing.routes.ts`). A member reads only her own inquiries (`GET /api/housing/my/inquiries`); a lister reads and answers only the inquiries on her own listings, and sees the asker as an alias with no id or avatar until the asker approves sharing; the street address reaches only the lister, an administrator, and a member the lister has answered. The staff routes (`/api/housing/admin/*`) are `requireRole('ADMIN')`; a moderator reaches none of them. No search, feed or export reads housing rows, except the member's own data export, which holds the listings and inquiries she made and nothing about inquiries other women sent her.

What is audited, so that "audited" means one thing. Staff **decisions** (checking a listing, deciding a provider check, entering or importing a listing) write `ADMIN_CONTENT_UPDATE` rows through `recordStaffAction`. Staff **reads** write a `DATA_ACCESS` row with `metadata.adminAction = HOUSING_DV_SAFE_VIEWED` through `recordStaffRead` (`athena-platform/server/src/services/staff-record.service.ts`) when an administrator is shown, and is not the lister of: the check queue (one row per request, naming every listing), a confidential listing by id or in the list (its street address), an inquiry thread on one she answers for the lister, a confidential listing she changes for the lister (address and DV-safe note), or a confidential listing she decides on from the check route, whose answer is the same view (a decision writes its `ADMIN_CONTENT_UPDATE` row and, beside it, this one; if the change takes the DV-safe claim off, the place counts as confidential for this purpose, because the answer still carries its address and note). A row records who, which listings, which fields were in the response, when, and the reason if one was given with `?reason=`; it never holds the address, the note, a name or the words of a thread. A reason is not demanded. A failed audit write is logged under `audit DATA_ACCESS` and does not stop the page. Not audited: an administrator reading her own listing, a lister or asker reading their own, and ordinary (non-confidential) listings. Find them in the audit-log viewer with `adminAction=HOUSING_DV_SAFE_VIEWED`. Pinned by `athena-platform/server/src/routes/__tests__/housing.supply.test.ts`.

## Rules

1. **Deny by default.** Every non-public route must call `authenticate`; role checks via `requireRole` — never by trusting client-supplied fields. "Public" is a list, not a habit: a route may be reached without signing in only if it is named, with its reason, in `src/config/public-routes.ts`. `npm run check:route-auth` (CI) walks every router mounted in `src/index.ts` and fails on a route with no `authenticate` that is not on the list (or a list entry that no longer matches a route), and `src/__tests__/route-auth-coverage.test.ts` sends the running app an anonymous request to every other route and fails unless each answers 401.
2. **Ownership checks on every object access** — the ID in the URL is never enough. The one obvious way to do it is `requireResourceAccess({ load, allow })` in `src/middleware/resource-access.ts`: it loads the thing, asks a policy (`ownedBy`, `participant`, `orgMember`, `hiringStaffOf`, `hasRole`, joined with `anyOf`), and answers 404 for a missing thing and a refused one alike, so the answer never says which ids are real. A policy that throws, or answers anything but `true`, is a refusal; a staff role only counts once the account has a second factor. Routes that still check by hand (find, then compare) follow the same rule, someone else's thing reads as 404, and move onto the helper as they are touched. Public resources (an organisation, a job) keep 403 for a stranger who tries to change them, because the stranger can already see they exist. A stored file's owner is read from its key (`<folder>/<user id>/<file>`), so a key is a path of plain names or it is refused: `normalizeUploadKey` in `athena-platform/server/src/routes/media.routes.ts` rejects a `.` or `..` segment, which would otherwise let `resumes/<my id>/../<her id>/cv.pdf` pass the owner check and resolve to her file on disk, and `athena-platform/server/src/utils/public-uploads.ts` does the same for the `/uploads` file server, which serves only the public folders.
3. **Request bodies never name the owner, the role, the verification status or the price.** A body that goes to the database is read through a strict schema (`parseStrict` in `src/utils/request-schema.ts`, which answers 400 naming an unknown field) or by picking named fields, and the write is built from the result with the owner taken from the session. `npm run check:raw-body` (CI) fails on `update: req.body`, `create: req.body`, `data: req.body`, `...req.body`, `Object.assign(x, req.body)` and rest-destructuring of the body in `routes/` and `services/`: Prisma reads a nested object as a write on a relation, so an unparsed body can reach columns that are not on the form.
4. **Admin actions are audited** via SecurityAuditService / security_audit_logs.
5. Subscription tier gates features, never authorisation (`requireSubscriptionTier` is not an authz control).
6. The Next.js middleware auth gate is coarse; real enforcement is server-side.

## Standing: who may act, and which rooms need a completed women-only check

Roles say what a member is; standing says whether she may act at all. Two things are held against standing, in two levels, and the first is central so that no route has to remember it.

**The floor (every write, enforced once).** `authenticate` reads `womanVerificationStatus` and `dateOfBirth` on every request (`athena-platform/server/src/middleware/auth.ts`) and `accountStandingRefusal` (`athena-platform/server/src/middleware/account-standing.ts`) refuses every POST, PUT, PATCH and DELETE from an account a reviewer has REJECTED, whose recorded date of birth is under the platform minimum (`MINIMUM_AGE_NOT_MET`), or that has no date of birth on file (`DATE_OF_BIRTH_REQUIRED`: an account made before one was asked for, which can read everything and is asked for it once, on its first write, and refused every write until it answers; the date is her own word and is not described as verified). Reading stays open, so she can see why and where to go. What she can still do is a short list written out in that file, not a prefix rule: sign in and out, change her password and manage her sessions (`/api/auth/`), exercise her privacy rights (`/api/gdpr/`), reach safety and domestic-violence support (`/api/safety/`), write or delete her own safety plan (`POST` and `DELETE /api/impact/safety-plan`, which live under another prefix), read her notifications, file a report or agree to a policy (`/api/compliance/`), appeal (`POST /api/appeals`), correct or delete her own account, send her women-only verification evidence, give her date of birth (`POST /api/users/me/date-of-birth`), and cancel a subscription. A new route is refused for a refused account until somebody decides it belongs on that list. An account that is merely UNVERIFIED or PENDING passes the floor: everyone self-attests when she registers, so the only account the floor can turn away is one a reviewer has already looked at and refused. `athena-platform/server/src/__tests__/route-standing-coverage.test.ts` walks every mounted write route and fails on one that is neither behind `authenticate` nor public nor named, with its reason, in `STANDING_EXEMPT_OPTIONAL_AUTH_WRITES` (`athena-platform/server/src/config/woman-gate-policy.ts`): a write that reads the member from `optionalAuth` would otherwise be a way round the floor. There is none today.

**A completed check (a few rooms).** `womanVerificationStatus = VERIFIED` means a person has approved the evidence she sent. It costs her a few minutes and costs a reviewer time, so it is asked only where a promise is made to other members. The decision is recorded in `athena-platform/server/src/config/woman-gate-policy.ts`, with the reason for each row, and enforced by `requireWomanVerifiedFor` / `womanVerifiedRefusal` (`athena-platform/server/src/middleware/woman-gate-surfaces.ts`):

| Surface | Needs | Enforcement today | Why |
|---|---|---|---|
| Publishing a mentor profile | VERIFIED | always on (`mentor.routes.ts`) | A mentor profile asks other women to trust her with their careers and money. |
| Confidential, DV-safe housing listings | VERIFIED, or Safe Mode | always on (`housing.routes.ts`, `mayEnterConfidentialSpace`) | The listings protect women leaving violence. Safe Mode is the one deliberate exception: a woman who needs a bed tonight cannot wait for a review. |
| Joining a private group: asking to join, or being approved, added or suggested by someone else | VERIFIED | **off until `WOMAN_VERIFIED_REQUIRED_FOR` names `private_groups`** (`group.routes.ts` for the member asking and for an admin approving a request, `group-chat.service.ts` for an admin adding a member or a member suggesting one) | A closed room's admins approve whoever asks. A request filed on someone's behalf, or an admin who adds them, must not bring in the account the room does not admit. |
| Requesting a creator payout | VERIFIED | **off until `WOMAN_VERIFIED_REQUIRED_FOR` names `creator_payouts`** (`creator.routes.ts`) | Payouts are paid from other members' gifts and subscriptions; this is the one place the platform spends members' money on the self-attestation alone. |
| Everything else: posts, comments, reels, public groups and channels, events, jobs and applications, learning, the marketplace, AI, direct messages, stories, housing enquiries and listings | the floor only | always on (central) | No promise about who else is in the room is made. Housing listings and enquiries already also need the host checks in `docs/security/host-employer-checks.md`. |

**Decision for the founder [FOUNDER].** The last two surfaces are built and tested but deliberately off. Turning them on before a person is reviewing women-only requests would shut every member who has not been reviewed out of private groups and every creator out of her payouts until someone gets to her. To switch them on, set `WOMAN_VERIFIED_REQUIRED_FOR` on the API host to `private_groups`, `creator_payouts`, both separated by a comma, or `all`, and record the date and who decided here. The server logs one warning at start for a name that matches no surface. Employer and provider badges are not asked for before posting a job or a course: the badges are a signal members can read, not a gate, and a gate would need a decision about what an unbadged employer may still do. That is also the founder's call, and is not made here.

**What the apps do with a refusal.** A refusal carries a code, `WOMAN_VERIFICATION_REQUIRED` (complete the check) or `WOMAN_VERIFICATION_REJECTED` (a reviewer refused it; appeal), a sentence in `message`, and `setup`, the page that fixes it. The web app shows one notice in the dashboard with the sentence and a link (to `setup` for a member who can complete the check, to the appeal for one a reviewer refused), whichever request was refused, and the request still fails with the sentence on the button that was pressed (`athena-platform/client/src/lib/woman-gate-refusal.ts`, `athena-platform/client/src/components/safety/WomanGateRefusalNotice.tsx`). The phone app adds where to finish the check to the sentence, because the check itself is done on the website (`athena-platform/mobile/src/utils/apiErrors.ts`).

## Locking an account

"Sign out everywhere" ends the sessions that exist and nothing more: whoever holds a stolen password signs straight back in. A member who suspects someone else has her account can lock it (`POST /api/auth/lock`, signed in; or the one-time "this was not me" link in a new-device sign-in email, `POST /api/auth/lock-by-token`, no session needed). Locking sets `User.lockedAt`, ends every session and closes the live sockets, and mails the address on the account a link that unlocks it. While it is set, password sign-in, Google, Facebook and refresh all refuse in the lock's own words (no appeal wording: nobody on staff did it), and `authenticate` refuses any token that slipped in while the lock was being made. Unlocking (`POST /api/auth/unlock`) is by that emailed link, works once for 24 hours, issues no session, and ends any that appeared in the meantime; a new link is one request away (`POST /api/auth/request-unlock`, which answers the same for every address). A staff account that has not enrolled a second factor may still lock, because locking only ever shuts a door. Both link kinds are stored hashed, spent by deleting the row, and audited (`ACCOUNT_LOCKED`, `ACCOUNT_UNLOCKED`). Behaviour is pinned by `athena-platform/server/src/routes/__tests__/auth.account-lock.test.ts`.

## Organisations: where one tenant ends and the next begins

An organisation (a company, a training provider, a host employer) keeps its own books, stock, money records, jobs, apprenticeships and the applications to them, and has a team. These are the rules that decide who, inside and outside it, may see and change them.

1. **One definition of "in the organisation".** A member is someone whose `OrganizationMember.acceptedAt` is set. The row exists from the moment an owner types her address into the invite box, and until she says yes it grants nothing. That is `assertOrgMembership` and `memberOrganizationIds` in `athena-platform/server/src/utils/org-scope.ts`, and `ACCEPTED_MEMBER_WHERE`, `HIRING_MEMBER_WHERE`, `POSTING_MEMBER_WHERE` and `canManageJobApplicants` in `athena-platform/server/src/services/hiring-access.service.ts`. Every route that takes an organisation's id, or the id of one of its rows, asks it. That includes applying for an organisation's verified mark, and the approval that sets it (`canVerifyOrganisation` in `athena-platform/server/src/routes/verification.routes.ts`): an invited owner or admin who has not answered can do neither.
2. **Scope comes from the caller, not from the request.** An `organizationId` in a query string or a body may narrow what the caller can already see and never widens it: organisation ids are public (the directory hands them out), so an id is not a credential. A row in an organisation's books belongs to the organisation. The id of whoever filed it is recorded, and is not a key, so a person who has been removed from the team cannot go on opening what she filed: accounts, journal entries, draft returns, bank-line links. (They could, until 2 October 2026: the by-id routes asked for ownership first and for any membership row second.)
3. **Roles inside.** Every accepted member shares the books and the stock. Money records (`/api/money/transactions`) are not shared: they are a book each member keeps for herself, so a record is listed, changed and deleted only by the member who typed it, and naming an organisation on a new one needs accepted membership of it. Only hiring staff (an accepted OWNER, ADMIN or RECRUITER, or a member given posting rights) see who applied, move applicants or read a résumé attached to an application. Writing a listing needs OWNER, ADMIN or posting rights, and changing the team needs `canManageTeam` or ownership. A return filed in an organisation's name is changed only by the member who filed it, and only while she is still a member.
4. **What a refusal says.** On the books routes someone outside the organisation is answered 403. On the applicant, apprenticeship and résumé routes she is answered 404, where even the existence of an id should not be confirmed. Neither names the organisation's data.
5. **No row-level security, on purpose.** The API connects to Postgres with one database role. A row-level security policy decides by the connected database user, which is the same for every member of every organisation, so it would add no isolation here. Making it decide by the signed-in member would mean setting a session variable inside every transaction of every route, and would put the rule in two places that can disagree. The production database is also shared with an application this repository does not model, which has no such policies to stay consistent with. The isolation is the rules above, held in the code; it is held to them by `athena-platform/server/tests/integration/tenant-isolation.test.ts`, which CI runs against a real Postgres (`npm run test:integration`). It builds two organisations with the same rows and requires a member of the other organisation, someone invited who has not answered, a bookkeeper removed after filing, and the owner of one naming the other's id each to be refused every read and write on the books, stock, tax, money records, jobs, applicants, apprenticeships and résumés, with nothing of the other organisation in the answer and every row unchanged afterwards. The unit suites beside the routes (`accounting.scope`, `accounting.by-id.scope`, `tax.returns.scope`, `banking.ledger-scope`, `money.scope`) hold the same rules with a mocked database. If a second database role is ever given to the API (a read-only role for reporting, say), revisit this: that is the point at which row-level security would start to add something.
6. A new route that takes an organisation's id, or the id of a row an organisation keeps, earns a probe in that suite.

## Known gaps (tracked)

- Two of the four completed-check surfaces are off pending the founder's decision above, and which surfaces must be on at launch is that decision. Until then a self-attested, unreviewed account can join private groups and request payouts.

- The cross-member suite (`tests/integration/idor-matrix.test.ts`, run by CI against a real Postgres) covers seven kinds of thing — a message and its conversation, a job application, a marketplace order, a portfolio holding, an invoice, a notification and a résumé file — for member B against member A, and for a caller with no token. It is the start of a matrix, not the whole of one: a new route for one of those earns a line in its row, and the other resources (groups, events, courses, housing and so on) still have only the unit tests beside their routes. The organisation-scoped surfaces (books, stock, tax, money records, jobs, applicants, apprenticeships, résumés, team) are the exception: `tests/integration/tenant-isolation.test.ts` covers them, as described above.
- Many handlers still do their own find-then-compare instead of calling the helper, and some answer 403 where this document says 404 (`grep "ApiError(403" src/routes`). Each is a small change to move onto `requireResourceAccess` when the route is next touched; none is known to grant access it should not.
- `app-backend` legacy routes (69 files) need a route-by-route authz review before that line ever serves production traffic.
- A second factor is required for MODERATOR, ADMIN and SUPER_ADMIN in production (`staffTwoFactorRequired` in `roles.ts`, applied in `authenticate`): a staff account without one is refused everywhere except the enrolment routes. It can be switched off outside production only.
