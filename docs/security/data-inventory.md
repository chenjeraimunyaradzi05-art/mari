# ATHENA Data Inventory
_Version 1.0 — 2026-08-18. Source of truth for schemas: `athena-platform/server/prisma/schema.prisma` (active line), the retired app-backend schema (quarantined, no longer in this repository). Storage: Neon Postgres (active); member uploads in S3 (`ap-southeast-2`) in production, with `athena-platform/server/uploads/*` as a development-only scratch folder (see gaps)._

## Where data must NOT be

- Git history (env files existed in tree — rotate; see SECURITY-HARDENING-CHANGELOG.md)
- Client-side storage beyond the session token (localStorage token noted as an accepted risk pending cookie migration)
- Logs: no passwords, tokens, personal details or message bodies. The logger removes them itself, whatever a caller passes it (`athena-platform/server/src/utils/logger.ts` and `log-scrub.ts`): values under keys such as `password`, `token`, `email`, `phone`, `ip`, `content` and `query` are replaced; email addresses, bearer credentials, web tokens, long hex tokens, phone numbers and the arguments a database error echoes back are removed from any text, error messages and stacks included; a user agent is cut to 120 characters; and the request log names the route (`/api/wellness/share/:token`), not the path, because some paths carry a credential. `athena-platform/server/src/utils/__tests__/logger.contract.test.ts` drives the real code with canary values and fails if one comes out. This works by shape. It cannot see a name or a sentence somebody wrote, so nobody should log one: a log line finds a row by its id. How long the host keeps them: see `athena-platform/docs/runbooks/ONCALL.md`, "Logs: what is in them and how long they are kept"

## Gaps

1. Uploads. In production the API refuses to start without S3 and a `CDN_URL` that is not the bucket's own address, and never writes a member's file to the container disk; résumés, documents and files sent in a conversation (`resumes/`, `documents/`, `chat/`) are addressed at the bucket (never the CDN) and read only through the API, by a signed link that lives five minutes: a résumé by the owner or by hiring staff on an application it was attached to, a chat file by the people in that conversation now. Every image is re-encoded on upload (EXIF, GPS and the rest dropped, orientation kept) and every video and recording is copied without its tags, so a file never says where it was taken. A chat file is deleted when its message expires, is unsent, or its member is erased. What the code cannot enforce is the bucket side: Block Public Access on, the CDN limited to the public folders (avatars, covers, posts, videos, thumbnails, captions, sounds), and `GET /health/launch-readiness?probe=media` run once after setting it up, to prove from outside that a private file cannot be read and a public one can. Files sent in conversations before October 2026 went up as public post pictures, reels or sounds and stay that way (`athena-platform/docs/runbooks/MEDIA-BUCKET.md`). **[FOUNDER: create the bucket and CDN per `athena-platform/infrastructure/README.md` and run that check.]**
2. AI prompt/response retention undefined — define and enforce (see ai-system-card.md).
3. Field-level encryption is in place for the most private records (safe-chat message text, health entries, medications, health notes, booking reasons, safety plans and TOTP seeds: AES-256-GCM under `DV_ENCRYPTION_KEY`, with `HEALTH_ENCRYPTION_KEY` and `TOTP_ENCRYPTION_KEY` as optional keys of their own; `athena-platform/server/src/utils/encryption-key.ts`, threat model and rotation in `athena-platform/docs/runbooks/ENCRYPTION.md`). The key is a single value in the API host's environment, not a KMS-managed key: the API decrypts on every read, so this protects a database copy, not against the host itself. Open: evaluate KMS envelope encryption, and record where the key backup is held and who can reach it. (Verification documents are not stored by ATHENA: Stripe Identity holds them and is asked to redact them once a decision is made.)
